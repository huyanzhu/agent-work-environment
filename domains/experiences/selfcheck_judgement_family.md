判读"读数 / 回归结论 / 台账状态"时先问三句：**我读的是权威源吗**（做法 A）· **判据本身自检过吗**（做法 B）· **语料与判据同代吗**（做法 C）· **统计口径完整吗**（做法 D）。⛔ 不要先按读数下结论 —— 这类坑的典型形态是**读数看着大幅退化，实际检索/代码一点没变**。

**做法 A · 读数源先对齐：认权威源 + 当场现取，不认间接件、旧台账与自述（P5/P19/P63/P73）**
- 探针只认 `.aios/_aios-activation.probe.log` 那一份；`%USERPROFILE%\.dsh\` 下那份**跨 root 共享**、混入过 FocusRoute 读数 ⇒ 同一条 query 在两份文件里读出两个结论（P5）
- `.aios/focus-card.json` 会长期停在**旧会话**（里面的 `session` 与 `cardKey` 都是老的），看起来像"当前焦点卡" ⇒ ⛔ 不用它判当前焦点、更不用它的 `writerPolicy` 判当前版本；焦点用**卡内 Event Log + 探针 `stage4{focusBasis}`**（P19）
- 台账/交接写「待重启 / 新版本未加载」**不等于现状**：先读最后一条 `'"ev":"apply"'`，看 `policy` 尾串是否已含新版本、且其后无新 apply ⇒ **新版本其实早就在跑**，⛔ 别按台账去等重启 / 白跑一轮验收（P63·搜 apply 要用带引号的 JSON 形态，裸 `ev=apply` 文本恒 0 条）
- **Agent / 子 agent 的自述不能当读数**：它按**语义**判失败类型，Runtime 按**正则**判 ⇒ 两边会不一致（观察：子 agent 报"全程无知识型失败"，探针却有 `ok:false` + `inject{gap}`）⇒ 判读一律以探针为准，自述只作线索（P73）

**做法 B · 判据/回归门先自检，再拿它判生死（P86/P7/P74/P75）**
- 回归门脚本必须**先用已知基线语料复现基线读数**，再判语料生死：观察 hybrid 只回传 `kind/title` ⇒ `_rel()` 的 `title+content+matched` 三段判定**全失败** ⇒ 读数从 `8/7/7 · 13/14/10` 掉成 `8/5/5 · 6/9/17`，据此**误判"语料退化"并回滚了一版正确的族卡**（P86）⇒ 读数漂移先查**脚本**，⛔ 不先查语料
- 判据要对着**语义明确的信号**：用 `has-edit`（真的改过工作）判「有改动」，⛔ 别用 `turnHadSuccess`（只读卡 + 跑只读命令也会算"有改动"）；同理 `ok:false` 不是"全部失败"（pwsh 非零退出不计入）（P7）
- **原词档只能验接线，判据要取换词/语义档**：用「经验原文」当 query 的命中率是字面重合，不是泛化能力（观察原词 8/8、换词 4/8、语义 2/8）⇒ 测前先写"同场景不同说法"的 paraphrase 集（P74）
- **看似合理的排序/阈值改动必须用 N≥30 对照**：给经验召回加「标题重合优先」直觉上能修好，观察 top1 相关 10→9、误报 12→13（无信息标题被系统性压低）⇒ 改前先定对照表与判据，改后必须复跑（P75）
- 区分两问：读数大跌 ⇒ ① **脚本对吗**（做法 B 自检）② **判据与语料同代吗**（做法 C）；两问都排除后，才允许怀疑语料/代码

**做法 C · 语料改动 = 一个事务：期望集同代 + 新条目余量单查（P85）**
- 族卡替换 / 新增 / **改标题** 后，场景探针 `FAMILIES` 的**期望条目集必须在同一改动里对齐**；否则新增族卡单元全被记成误报 ⇒ 假回归（观察：词面 top1 **11 → 2**、混合 12 → 7，实际检索没退化）（P85）
- 新增坑条目要**加进它所属族的期望集**（P83/P84 属 Runtime 族但没加 ⇒ 该族混合 top1 由 12 **假掉到** 8）；族卡改标题也要同步（否则探针直接报"期望条目不在语料"）（P85 变体）
- 每个新条目要**单查纯向量余量**：观察只超阈值 **0.0043**（`sim=0.5543` vs gate 0.55）就翻一条 N=30 误报（10 → 11）⇒ 候选先试算 sim 再落盘，落盘后做**内存消融归因**（索引不动、只换参与打分的 corpus）定位到唯一越线条目，⛔ 别整批回滚（P85 变体）
- 分清**通道与截断**：族卡（`kind=experience`）**不进混合通道**（混合候选空间只有 `pitfall` + `digest`）⇒ 想改混合读数只能动 pitfall/digest/期望集；族卡与「同义现象」改的是**词面通道（=运行时实际召回）**。⚠️ 另有一条**截断**：文件的语义向量 = `标题 + trigger/keywords/condition/alias + 正文前 1400 字`（总长截 2000）⇒ **卡尾的「同义现象」常被截掉、根本没进向量**（观察推送族卡 embed_text 1933 字）⇒ 补语义覆盖要补在**卡头**（frontmatter 与正文开头），⛔ 别只补在卡尾。

**做法 D · 统计口径要逐条、逐通道（P8/P58）**
- `CARD_CMD_RE.exec()` 只取**首个匹配** ⇒ 一次 pwsh 里写多条 `claim/release` 只记第一条 ⇒ 覆盖/计数类判据一律**逐条扫描**（`exec` → `matchAll`/`finditer`），并用"我写了 N 条、应记 N 条"对账（P8）
- **路径匹配一律用 `[\\/]` 或 `path.normalize`**：按 `'capabilities/'` 子串匹配在 Windows 反斜杠路径上系统性漏计（观察严格 24 次 vs 宽松 201–207 次，漏 ≈88%）⇒ 统计脚本新增后先与人工抽查 2–3 个样本对照（P58）
- 族卡「**同义现象**」行**只喂词面通道**（它位于卡尾，且文件向量只取正文前 1400 字 ⇒ 常被截掉）⇒ 补语义覆盖要补在**卡头**（`trigger/keywords/alias` 与正文开头）
- 别把"调用数"当"消费数"：工具被调用 ≠ 内容被采纳
