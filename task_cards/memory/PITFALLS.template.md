# PITFALLS — 踩过的坑（**模板 · 怎么新增一条**）

> 复制本文件为 `PITFALLS.md` 后开始记。**只收「会再犯」的坑**；一次性的调试细节留在卡里。
> 每条四栏：**现象 · 触发条件 · 处置 · 来源**。⛔ 不留「可能会踩」的猜测。

## 一条的标准形状

```markdown
| **P1** 🔴 | **一句话把坑说清**（现象 + 为什么会咬人） | 什么情况下会踩（触发条件要具体到"你当时在干什么"） | 怎么防 / 怎么判读（最好是一条能跑的检查） | 日期 + 实物指针（文件:行 / 命令输出 / 卡 ID） |
```

严重度：**🔴** = 会让你得出错误结论或静默失败；**🟡** = 会浪费时间但不致错。

## 三条纪律（来自维护手册）

1. **只在真踩过时登记** —— ⛔ 不留"可能会踩"的猜测。
2. **写清触发条件** —— 否则下次认不出来。
3. **修掉之后标"已修 + 修法"，⛔ 不删除** —— 保留防错价值。

## 示例（虚构）

| **P1** 🔴 | **配置写坏了不报错，静默回落到缺省**：开关"看起来开了"但实际没生效 | 用手写工具改 JSON 配置（尤其带 BOM 的编码） | 写完读回二进制头三字节；判读「开关不生效且零报错」先查编码 | 2026-01-01 · `<命令输出>` |
| **P2** 🟡 | **读数全绿但退出码非 0**：脚本末行打印特殊字符，在窄编码终端抛异常 | 在代码页非 UTF-8 的控制台跑打印中文/符号的检查脚本 | 判读**先看读数再看退出码**；脚本把 stdout 钉成 UTF-8 | 2026-01-02 · `<file:line>` |
