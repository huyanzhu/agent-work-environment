# 任务卡描述规范：`Goal` 与 `Next Action`

## 怎么做

```text
① 写 `Goal`（**宿主想达成什么结果**）
     一句话说出"做完之后世界有什么不同"，并写清**任务对象与领域**（专名保留原写法）；
     ⛔ 不写实施步骤 / 文件路径 / 测试命令 / 施工依据 / 恢复入口（它们归各自字段）。

② 写 `Next Action`（**当前在对什么对象做什么**）
     用「**动作 + 工作对象**」：
       正例 `按 REBUILD_PLAN §7 推进前端（S6）`
     在等外部 ⇒ 必须带上"到位后做什么"：
       `等待 <谁> <什么>；到位后 <动作 + 对象>`
     ⛔ 不以"等待 / 用户验收 / 进入观察期 / 收口归档"作为这条字段的**全部内容**。

③ 自检
     `python scratch/_card_description_lint.py`    # 机械检查 G1–G3 · N1–N4

④ 同步更新
     方向或下一步改变时，**同步更新**这两条；旧 `Goal` 不得继续主导。
```

**三层次必须分离**（Goal ≠ 查询 ≠ 相关）：

| 层 | 内容 | 承载 |
|---|---|---|
| 工作记忆层 | `Goal`：宿主希望实现什么结果 | 任务卡 |
| Runtime 检索输入层 | `Query representation`：用什么表达去找材料 | Runtime（用 `Next Action` 的对象派生短语，⛔ 不把整段 Goal 当查询串） |
| 候选评估层 | `Relevance`：找到的材料是否真的适合当前目标 | Agent / 独立核验者（⛔ **关键词命中 ≠ 相关**） |

## 是什么

本规范规定任务卡中**两条字段该怎么写**：

| 字段 | 回答什么 | 谁读它 |
|---|---|---|
| **`Goal`** | 宿主**想达成什么结果** | 人（语义依据 · 写卡时对照） |
| **`Next Action`** | 当前这一步**在对什么对象做什么** | **Runtime**（焦点对象的**唯一来源** ⇒ 检索输入） |

**为什么需要它**：Runtime 要"把卡交给检索"，就必须先拿到**工作对象**；而实测表明，
只有写成「动作 + 工作对象」的 `Next Action` 才能被机械提取 ——
**卡怎么写，决定了 Runtime 能拿到什么**（现行 12 张新模板卡：`Next Action` 合规 **4/12**，
与「字段产出器」的可接入子集 **2/12 完全一致**）。

**状态**：**待验证的设计要求** —— 尚未批量落地（⛔ 未改历史卡 · ⛔ 未改 Runtime）；依据见 §规范/依据。

## 规范

### 1. `Goal`（G1–G6）

```text
G1 表达**结果**，不只是动作
     弱：`开发前端` / `修改代码` / `完善系统`
     好：`为目标用户交付具有清晰视觉层次与一致交互体验的产品首页`
     判据：能否说出"做完之后世界有什么不同"？只说得出"做了什么动作" ⇒ 不合格
G2 保留**足以区分任务的对象与领域**（技术专名保留原始写法：`Next.js` / `Supabase RLS` / 子系统名）
     判据：两个不同任务会不会写出同一句 Goal？会 ⇒ 区分度不足
G3 ⛔ 不承担"检索查询"的职责：不堆关键词 / 实现步骤 / 文件路径 / 测试命令
G4 用**宿主的工作语言**（中文任务写中文）；⛔ 不要求手工维护英文版
     （是否需要英文检索键属 Retrieval 的独立问题，⛔ 不得转嫁给写卡者）
G5 **长度 ≤ 180 字符**，且 ⛔ 不含元信息
     元信息 = `施工依据` / `恢复入口` / `旧实现基线` / `新仓库` / `基线` / 盘符路径
     ⇒ 它们应归 `Knowledge Used` / `Resume Point` / `Deliverables`
G6 方向改变后，**旧 Goal 不得继续主导**；"当前卡是否对应当前工作"必须有可靠依据
     （⛔ 不凭标题相似度或 mtime 猜；多卡关联不明 ⇒ 保留 `unknown`）
```

### 2. `Next Action`（N1–N4）

```text
N1 **含「动作词 + 受控工作对象词」**（词表见 §3）
N2 **不得只表达"等待 / 验收 / 归档"**：含这类成分时，必须按 N4 同时给出「到位后 动作 + 对象」
     ⛔ 整条只有等待/验收/归档 ⇒ 等于没有工作对象
     ⚠️（原措辞"不以非施工词开头"**与 N4 冲突** —— 等待型本就要以"等待"开头 ⇒ 已废止）
     ⚠️ 判据实现：只要**某一段**（含"到位后"那段）能提取到「动作+对象」，即视为通过
N3 **长度 ≤ 120 字符**（口径 = `tools/task_start.py` 的 `_next_action()`：**首行 + 缩进续行**）
     ⚠️ 实测：某卡 Next Action 首行很短但**续行 984 字符** ⇒ 只读首行会漏报 ⇒ 检查器必须用同一口径
N4 **等待型必须自带"到位后做什么"**：`等待 <谁> <什么>；到位后 <动作 + 对象>`
     ⇒ "等"本身可以写；但它**不能是这条字段的全部内容**

N5 **卡中只允许一个 `Next Action:` 行** —— 机制只读**第一条**（`task_start._next_action()`），
     第二行及以后**既不生效、也不报错**（**沉默失效**）
     ⇒ 历史 Next Action ⛔ **不写在卡里**，改写到 **`HANDOFF`**（交接文档）或由 `Event Log`
       （Stop hook 自动追加）+ 账本承担
N6 **⛔ 不得把「历史 / 已完成项」写进本条**（2026-10-12 新增）
     🔴 **首要理由 = 字段职责**（与任何消费者无关也成立）：本字段的定义是「**下一步** 做什么」；
        把"已完成项"写在这里属**字段职责混淆** —— "做过什么"归 `Event Log` / `Notes` / `Outcome`。
     判据：出现**完成态标记**（`已落地` / `已收口` / `已完成` / `已通过` / `已提交` / `已归档`）
     ⇒ **后果**（⚠️ 不是理由 · 顺序不可倒置）：抽取器取**词表里命中的那个词** ⇒
        历史陈述里的对象词会把当前对象顶掉
     实测反例（产品母卡 `TASK-20261008-001`）：
       `按 REBUILD_PLAN §10 推进 S9（S8 前端四页已全部落地并收口）`
       ⇒ 主句对象是 `S9`（**不在词表**），括号里的 `前端`（**在词表**）被取走
       ⇒ 焦点对象 = `前端`（**错**）· `categories` 跟着偏成 `设计/开发工具/集成`
       ⇒ 下游 8 个候选全是"设计"类噪声（离线实测读数见 `scratch/_stage4_offline_out1.txt`）
     改写：`推进 S9（DSH + Sandbox 执行链）的 runtime 适配` —— 括号**只放当前对象的限定语**；
       "哪一刀已收口"归 `Event Log` / `Notes`，⛔ 不进本字段
     ⚠️ 括号本身不违规（如正例 `推进前端（S6）`）—— 违规的是**完成态陈述**

正例（实测可提取）
  · `按 REBUILD_PLAN §7 推进前端（S6）`            ⇒ 对象 `前端`
  · `部署并替换域名占位`                            ⇒ 对象 `部署`
  · `改 AI-OS：获取类介入 runtime 化`                ⇒ 对象 `运行时`

反例 → 改写
  · `用户验收（试用系统、查看报告）；确认后归档`
    ⇒ `准备验收材料（试用系统 + 报告）；验收通过后归档本卡`                      ⇒ 对象 `文档`
  · `① 进入观察期（Human 定 ⇒ §二十九）：…`
    ⇒ `观察产品线数据积累（P0 侧不介入）；数据达标后按实测完善 AI-OS 运行时机制`   ⇒ 对象 `运行时`
  · `等待 M1/M2/M3 子流落地 → 执行 M4 评估层与 Governor`
    ⇒ `实现 M4 评估层与 Governor（M1/M2/M3 落地后接入）；随后打通 T070 端到端闭环`
      ⇒ ⚠️ 对象 `评估层` / `Governor` **尚未在词表** ⇒ 需先登记（见 §3）
```

### 2.5 `State`（**S1** · `Next Action` 能否被使用的前置条件）

```text
S1 `State` 必须反映**真实**工作状态 —— 若实际在施工，⛔ **不得**用 `Waiting` / `Reviewing` / `Active`
   掩盖（"名义让位产品线"这类说明应写进 `Notes`，`State` 仍写 `Executing`）。

依据（实测）：本卡 `State = Waiting —— 名义让位产品线；**实际在推进本体**`，
  卡内**自述**实际在推进 ⇒ 字段产出器据 S1 拒发字段（`reasons = state-not-executing`）。
  🔴 **结论**：`Goal` 与 `Next Action` 都写到合规，**只要 `State` 不真实，依然不可接入** ——
  三条字段是一个整体，任一条不实都会让下游拿不到字段。

改写示范：`State: Executing`（并把"名义让位产品线 · Human 逐轮特批"移入 `Notes`）

### 2.6 `State` 的**占用语义**（S2 · Human 2026-10-12 裁定）

```text
S2 `State` **不只是描述，而是「占用声明」**：想用一张卡就必须显式占用，本轮结束就显式释放。
     · 占用：`python tools/task_card.py claim <TASK-ID>` —— `Planning` / `Parked` ⇒ `Executing`
     · 释放：`python tools/task_card.py release <TASK-ID> --state=Parked|Completed`（**必填**）
     · 校验：`python tools/task_card.py states`（只读 · 报**缺失**与**值域外**写法）

值域（与模板同步 · 唯一来源）：
    Created | Planning | Executing | Parked | Blocked | Waiting_Human | Reviewing | Completed | Archived
    `Parked`（2026-10-12 新增）= **暂停但未完成、可恢复**
      ⛔ 不复用 `Planning`（= 尚在规划、尚未开始）· ⛔ 不复用 `Waiting_Human`（= 等的是**人**）

🔴 三条硬约束
    ① **Runtime / 脚本绝不自动改 `State`** —— `release` 不推断"完成与否"；**停止 ≠ 任务结束**
    ② 同一 Worker 同时只能占用**一张**（`claim` 检测到别的 `Executing` ⇒ **拒绝并报告冲突**，
       ⛔ 不自动替其他卡释放）
    ③ `Completed` 只表示"已完成"，**归档仍是独立动作**（`archive --confirm`）

由此得到的收益（机制面）：
    「焦点卡 = 被占用的那张」不再需要从 **git 脏文件 / 最近修改时间 / 全局 `Executing` 张数**去猜；
    读写事件（`cardEdits` / `cardReads`）退为**提醒触发**与**冲突审计证据**。

🔴 2026-10-16 **落地**（Human 裁定 · 本条从"设计意图"变为"已实施"）：
    焦点卡判据 = **本会话的占用声明**（Runtime `s.claimed` · 唯一来源 = `task_card.py claim|release`
    的**命令字面量**）；⛔ **删除** `env-unique-executing` 兜底
    （实测删前口径：兜底 **32** / 轨迹 **6** ⇒ **84% 的焦点卡是拿卡级状态冒充会话级占用**）。
    `claim` / `release` 另向卡内 `Event Log` 追加留痕（含 session id）⇒ 占用可跨会话追溯。
```

### 2.6 字段生命周期：**什么只填一次，什么要更新**

```text
| 字段 | 规则 |
|---|---|
| `Header`（Task ID / Type / Priority / Owner / Manager / Reviewer / Created） | **只填一次**（除 `Last Updated` / `Updated By`） |
| `Goal` | **基本只填一次** —— 建卡时写；**方向变更时重写**（G6：旧 Goal 不得继续主导）；⛔ 不追加历史版本 |
| `State` / `Current Step` | **每次更新**（覆盖式 · S1：必须真实） |
| `Next Action` | **每次更新 · 只保留一条**（N5）· ⛔ 不堆叠历史 |
| `Resume Point` | 变化时更新（覆盖式） |
| `Outcome` / `Confidence` | **收口时填一次**（重新打开任务才改） |
| `Knowledge Used` / `Deliverables` | **收口时定稿**（⛔ 不记流水） |
| `Event Log` | **追加**（Stop hook 自动 · 上限 20 条） |
| `Notes` | 累积；收口时清理 |
| **历史叙述**（"原本打算做什么 / 后来怎么改的 / 上一版 Next Action"） | ⛔ **不属于卡** ⇒ 去 **`HANDOFF`** / 账本 / 归档 |

🔴 **为什么必须这样**：卡是**工作记忆**（当前状态），不是流水账。
  把历史 Next Action 一行行堆在卡里，真实后果有两个：
   ① **沉默失效** —— 机制只读第一条，后面的既不生效也不报错（N5）；
   ② **Goal / Next Action 越堆越长**，直到被 `task_start` 的 180 字符截断（实测本卡曾 1019 字符、
      某卡 Next Action 曾 984 字符 ⇒ 都是堆叠出来的）。
  ⇒ 解法 = **一条当前 + 历史进 `HANDOFF`**。
```

### 3. 受控工作对象词表（**可扩展**）

```text
前端 · 后端 · 数据库 · 设计 · 测试 · 部署 · 检索 · 运行时 · 技能 · 记忆 · 文档 · 审核

扩展规则：遇到真实存在但词表未覆盖的对象（如 `评估层` / `Governor` / `端到端闭环` / `可观测性`）
  ⇒ **先登记**（同步三处映射：对象词表 / 领域职能短语 / 对齐类别），**再使用**
  ⛔ 不许为了通过检查而把对象硬塞进已有类目（那会让"对象"失去粗筛意义）
```

### 4. 依据（实测 · 2026-10-11）

```text
| 事实 | 读数 |
|---|---|
| `Next Action` 合规率 | **4/12**，且与「字段产出器」可接入子集 **2/12 完全一致** ⇒ 描述规范 = 可接入率上限 |
| 不合规分布 | 提不到「动作+对象」6 张 · 等待型未声明"到位后" 5 张 · 以非施工词开头 1 张 |
| `Goal` 合规率 | **4/12**：超长 5 张（最大 **1019** 字符）· 含元信息 5 张（产品卡含**六项**）· 无对象 1 张 |
| `Goal` 写作对照（3 真实任务 × A/B/C/D） | 唯一"语义正确命中"来自**最短**写法（17 字符 → `frontend-design`）；**加"目标效果"反而命中归零**（密度稀释）；加技术栈专名**几乎无增益** |
| 对象的价值 | 材料池按**对象/主题**组织（`trigger: 开始前端/UI 任务`），而 Goal 是**结果陈述** ⇒ 两维度正交；**对象是唯一能对齐的维度** |
| 对象 → 检索 | 名称硬门槛 + 对象对齐类别 ⇒ 候选池 **−76%/−90%** 而 precision@10 **不降** |
| 对象 → 焦点对象 | 施工态卡可提取（产品卡 `前端` ⇒ 检索 Top-5 **全对**）；等待/观察/归档型卡**提不到** |
```

### 5. 明确反对

```text
⛔ 要求 Agent 在每张卡里写一段**超长、双语、堆满关键词**的 Goal / Next Action
   —— 那是把**检索算法的问题转嫁给写卡者**，与"Runtime 承担机制职责"的目标直接冲突。
⛔ 把"能通过检查"当成目的（为了合规而凑对象词）。
```
