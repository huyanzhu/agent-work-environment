## 2. 新坑怎么进库（T21 · 五步流程）

> 背景：`PITFALLS` 已 89 条 + 6 张活跃族卡 + 9 条 digest，而**入库长期是手工批次**。本章把手工批次拆成可机械执行的五步 + 显式完成标准 + 回退路径。
> 一句话：**判层 → 写 → 余量预检 → 重建索引 → 回归门**；这五步里任何一步没过，不许宣称"这条经验进库了"。

### 2.0 三层入库形态 + 判定规则（什么时候该进哪一层）

| 形态 | 什么时候进这一层 | 位置 | 被哪个通道读到 |
|---|---|---|---|
| **族卡**（`kind=experience`） | 同一问题域 **+** 同一解法（"同解融合"），且有 ≥2 个不同触发说法；遇到要照做的一整套做法 | `domains/experiences/<x>_family.md` | **只词面**（= 运行时  实际召回）。⛔ **不进混合通道**（见 §2.0.1） |
| **PITFALLS 条目** | 单点坑、**会再犯**、没有同解 | `task_cards/memory/PITFALLS.md` 对应章 | 词面 **+** 混合（`pitfall` 是混合候选源） |
| **digest 行** | 要"**遇到就照做**"的**一句话** + 指针（短的那一侧） | `domains/experiences/inject_digests.md` | 词面 **+** 混合（`digest` 是混合候选源） |

- **族卡单元内 = 场景行**（场景 → 具体步骤/参数），⛔ 场景行不是"新条目"，不单独占编号（PITFALLS 的编号体系与族卡的单元/场景是两套）。
- 判层还要连问三句：**① 会再犯吗**（一次性调试细节 ⇒ 留在卡里，不进库）· **② 有同解吗**（有 ⇒ 并进已有族的场景行，别新建单元）· **③ 机制能修吗**（能修就先去修；任务卡族实测：6 个坑里 5 个在工具/runtime 层修掉后族卡就冗余了 ⇒ 判定依据是"**触发事件是否消失**"，不是"读数好不好看"）。

#### 2.0.1 三条实测通道事实（照抄不要意会）

1. **族卡不进混合通道**：`tools/probes/semantic_search.py:75-81` 的 `DEFAULT_SEMANTIC_SOURCES = ("pitfall", "digest")`、`DEFAULT_CANDIDATE_SOURCES = DEFAULT_SEMANTIC_SOURCES`（✅ 已核代码）⇒ 族卡（`kind=experience`）只在**词面通道**（`tools/experience_push.py` 的 `search`）参与。想改**混合**读数，只能动 `pitfall` / `digest` / 探针期望集；想改**运行时实际召回**，才动族卡。
2. **族卡向量文本的构成**（`tools/probes/semantic_search.py:136-157` `_file_entry`）= `title + trigger + keywords + condition + alias + body[:1400]`（✅ 已核代码）。⇒ 修正旧说法「语义向量只来自 frontmatter 四字段」：**还含正文前 1400 字**；实测推送族卡 `embed_text` 长 **1933** 字符，卡尾「同义现象」被截断、**未进向量**（✅ 实测）。⇒ 想让某句话影响语义，写在**前 1400 字以内**；写在卡尾「同义现象」里语义读不到（该行只喂词面）。
3. **词面打分的字段权重**（`tools/experience_push.py:65-73,416-453`）= `trigger/keywords/alias 3.0 · title 2.0 · rule_id/condition 2.0` + `body[:4000]` 以 `BODY_WEIGHT=1.0` 参与（✅ 已核代码）⇒ 「同义现象」行**进词面**（它属于 body），不进语义。

### 2.3 ③ 新条目 sim 余量预检

**为什么有这一步**：实测一个新条目 `sim=0.5543` 只超纯向量阈值 `0.55` **0.0043**，就翻了一条 N=30 误报（10 → 11 ⇒ 护栏 FAIL）。靠"看起来不相干"判断没用，必须算。

**分两段做**：
1. **落盘前 —— 候选措辞试算（不重建索引）**：用 `scratch/_p84_reword_.py` 那类一次性脚本，改**内存 corpus** 再算 sim。实测：候选 2 `sim=0.5149` vs 现行 `0.5377` ⇒ 选 0.5149 那版。（⚠️ 该脚本写死 P84，跨批要改。）
2. **落盘 + 重建索引后 —— 逐条复核**：

```powershell
& $py scratch/_new_entry_margin.py "<新条目标题子串>"   # ✅ 本手册跑过
& $py scratch/_new_entry_margin.py                     # ✅ 无参：列出所有"纯向量越线但词面=0"的条目 top
```

- 通过判据：**目标条目无任何 query** 在 `lex < 6` 的前提下 `sim ≥ 0.55`；脚本内置 `MARGIN_WARN=0.02`（余量 <0.02 记「⚠️ 擦线」⇒ 改措辞，别赌）。
- 脚本需要**索引与语料同代**（`load_index(..., corpus=...)` 会校验指纹，stale 直接抛错）⇒ 必须排在 ④ 之后。

### 2.4 ④ 重建索引

```powershell
& $py tools/probes/semantic_search.py build     # ⚠️ 本手册作者未跑（本批写域不含语料，禁重建）
```

- 语料一变索引就 **stale**，`load_index` **直接抛错不静默**（设计如此）：报 `index stale: 语料指纹 X != 索引 Y ⇒ 重跑 build`。本手册作者实测过一次这个报错（语料 fp `214fa897…` vs 索引 fp `cabaf522…`）。
- 记下**新指纹**并写进当批读数文档；指纹 = `id + embed_text` 的 sha1（`corpus_fingerprint`）⇒ 可逐字节核对"是否回到上一版"。

### 2.5 ⑤ 回归门（护栏 + 场景探针 + 覆盖审计 + 余量）

四条一起跑，**缺一条就不算过门**：

```powershell
& $py scratch/_guard_now.py                    # ✅ 护栏
& $py tools/probes/_scene_probe.py              # ⚠️ 写快照；--check 也是先比旧快照再覆盖写
& $py scratch/_family_coverage_.py   # ✅ 覆盖审计
& $py scratch/_pitfalls_lint.py                # ✅ 表结构
```

1. **护栏**（唯一有硬 PASS/FAIL 的）：混合通道 paraphrase **8/8 · 7/8 · 7/8**；N=30 **top3 ≥ 14**、**误报 ≤ 10**（预注册基线）。⚠️ **词面读数脚本只记录、不判定**（同一语料实测：词面 `8/8 · 6/8 · 5/8` · `22/11/13/11`，混合 `8/8 · 7/8 · 7/8` · `23/13/14/10`）⇒ 判生死看混合，词面只记账，⛔ 别拿词面读数当护栏判据。
2. **场景探针**：**期望集必须与语料同代**（P85）—— 新增条目要加进所属族的 `FAMILIES` 期望集；族卡改标题要同步；否则族卡命中被算成误报 ⇒ **假回归**（实测：词面 top1 `11 → 2`、混合 `12 → 7`，检索其实没退化）。探针自带前置自检：期望条目不在语料里就 `return 2` 报「探针数据失真」。
   ⚠️ 探针**会写 `scratch/_scene_probe_snapshot.json`** ⇒ 只读场景先确认可写；快照被覆盖后，修复前的读数只能取自 `--check` 打印的 diff 原文，⛔ 别跨代比。

4. **撤族**（族冗余 / 实测负收益）：

## 3. 族卡形态与离线 A/B

### 3.1 单元 = 族；x 编码
- 族卡内每个 `**做法 X · …**` 单元 = 一条可检索单元；**x 编码** = 大场景标题 + 具体锚点（每锚点一条向量，单元相似度取 **max**）。整卡单向量会被稀释（本线早期 A/B 实测覆盖 `0.528` vs 分段 `0.689`）。
- ⚠️ **正式流水线只支持"一条语料 = 一个 passage 向量"**（`build_corpus` → `embed_passages`）⇒ x 编码多向量的优势**只在离线 A/B里拿得到**，进不了运行时。

### 3.2 七判据（**先写后跑**，⛔ 不改判据迁就结果）
`_ab_families.py` 头部预注册，一字未改：
` top1 ≥ A` · ` top3 ≥ A` · ` 漏 ≤ A` · ` 误报 ≤ A` · `paraphrase 不降` · `N=30 误报不升` · `N=30 top3 不降`。

### 3.3 替换形态 ≠ 加卡形态
A/B 的**替换形态**结论**不能预测**加卡形态（任务卡族实测：替换 FAIL → 加卡 PASS）⇒ **每次转正必须实测护栏**，⛔ 不搬 A/B 数字。

**转正成形的纪律（加卡，不是替换）**：
1. 族卡落 `domains/experiences/`（带 frontmatter），**旧 PITFALLS 条目一律保留、不删** —— 加卡形态 = 双方并存，两个通道各吃各的（§2.0.1）。
2. 然后走 §2.4 → §2.5（`build` → 护栏 → 探针），且**探针期望集同批同代**（P85）。
3. 回滚很便宜：删卡（+ 删 digest 行）+ `build` ⇒ 语料回到上一指纹（**记账用指纹核对**，逐字节可验）。

### 3.4 两个已实测的代价
1. **digest 会显著抬高 N=30 误报**：工具族 / Runtime 族实测 `10 → 11` ⇒ 护栏 FAIL ⇒ 这两族最终**无 digest**。
2. **只上族卡、不上 digest 是常态取舍**（自检与判据族、工具族、Runtime 族都是这么落的）；族卡已能让词面通道命中，digest 溢出的代价通常不值得。

### 3.5 自然出现验证（真实任务 · 判据只认三条）

离线护栏/探针只能证明"读数没退化"，**证明不了"真遇到时会来"**。要证后者，得派真实任务：

- **开关**：`.aios/experience_recall.json` 写 `{"enabled":true}`。⛔ **必须 BOM-less**（用 node/python 写，写完读回验证 · P32：`Set-Content -Encoding utf8` 带 BOM ⇒ 开关静默失效）。

## 4. 检索怎么改（runtime）

### 4.1 两个层次

| 层 | 位置 | 形态 |
|---|---|---|
| **失败触发** | `recallTriggerOf(result, toolName)` | 返回 `permission-error` / `exec-permission-error` / `exec-encoding-error` / `unknown-tool` / `knowledge-error` |

- 失败触发的**门**（别乱放宽）：来源门（`isExecToolName`）· 文件转储形态门（`looksLikeFileDump`）· 错误上下文门（`EXEC_ERROR_CONTEXT_RE`）· 退出标记（`EXIT_MARK_RE`，认 `[exit code: N]` / `EXITCODE: N` / `EXIT=N`）· 事实型短路（`RECALL_FACTUAL_EXTRA_RE`）· **限额类短路**（`RECALL_QUOTA_RE`：limit reached / rate limit / quota ⇒ 不触发）。
- 节点触发的四件套：**命中条件** + **每会话一次**（`Set<session>`）+ **探针事件** `ev=<name>-hint{state:injected|dup}` + **独立早退门**（否则别的开关没开时会被静默吞掉）。
- ⚠️ `tools/pre-execute` **只能 deny/allow，不能注入** ⇒ 节点提示只能在"动作发生的那一次工具结果之后"到达。
- ⚠️ `` 里另有一个**「经验过程匹配器」是纯函数、未接线**（`aios-activation.ts:3254` 注释自述"纯函数 · 未接线"）⇒ ⛔ 别当成已生效的召回逻辑。

### 4.2 改 runtime 的固定流程

## 6. Q5（能力是否真降低 agent 成本）对照实验的三条硬约束

> **失败案例**：同一可访问性走查任务跑了两臂，结论**作废** —— 但失败原因本身就是最值钱的发现。

### 6.1 那次是怎么废的（两硬伤）

| 硬伤 | 现场 | 后果 |
|---|---|---|
| **任务书里写足了能力内容** | 我给两臂都列了「对比度 4.5/3 · 键盘 · 焦点 · 语义名称 · 减动效 · 触控 44×44」= 能力片目录 | 测到的只是**投递通道**，不是**能力内容**（= P96 原形：任务书把被测变量提前发给所有臂） |
| **顺序不可逆** | 臂 A 先跑并修了 4 处；臂 B 面对的是**已修过的站点** | 两臂起点不同，发现数不可比 |

### 6.2 读数（作废但仍要留档）

| 臂 | 投递 | 读过 \capabilities/\ | 发现缺陷 | verify 检查点 |
|---|---|---|---|---|
| A（\TASK-20261102-016\） | claim 提示 + 域注入 3 次 | 是（全文） | **4** | 1129 → 1134 |
| B（\TASK-20261102-017\） | **0 次**（探针 \phase-inject\=0 · claimHint off） | **否** | **9** | 1134 → 1138（+4 条契约） |

### 6.3 能说的结论（两条，边界写清）

1. **投递通道的边际价值 ≈ 0**：臂 B 无提示、无注入、没读能力库，发现数**更多**（9 > 4）⇒ 在「任务书已给清单」的条件下，投递通道**没有可测收益**。
   - 与既往读数一致：阶段注入 15 次 / 0 次被采用；域注入 11 次 **0 错域但 0 次改变动作**。
2. **能力内容的价值仍未测**：两臂都拿到了同一份清单（我给的）⇒ 「有没有这个能力库」这件事**没有被对照**。⇒ **Q5 依旧未验证**，且有**反向倾向**（强 agent + 清单即可自查）。

### 6.4 下次要跑，必须同时满足这三条

1. **任务书零清单**：只写目标 + 验收方式（「让站点在键盘/读屏/弱视用户下可用，交付前说明你查了什么、怎么验的」），⛔ **不列检查项**、⛔ 不提 INDEX/能力名。
2. **平行不顺序**：两臂同起点 —— 用**同一份站点快照**（或两个同难度不同任务）；⛔ 不许一臂跑完再跑另一臂。
