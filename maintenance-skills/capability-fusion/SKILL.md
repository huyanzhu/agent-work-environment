# Capability Fusion（新能力怎么融合进域能力）

> 2026-11-02 建立（Human：「最好成文件内的 skill，让后续 agent 知道新 skill 怎么融合」）。
> 职责面：Maintenance（能力库结构）—— **不是普通 Work Task 的默认上下文**，不进 `task_start` 统一发现。

## 这份技能解决什么

**输入**：一个新能力 / 新 skill（外部的、自己攒的、从踩坑提炼的）要进能力库。
**输出**：它成为 8 个域能力中某一个的**做法（片）**，或者被判定为「不需要建」。
**硬要求**：⛔ 不再新增第 9、10…个能力文件；⛔ 不按阶段拆；⛔ 不建「通用」桶。

## 当前模型（2026-11-02 起）

```
capabilities/
├── INDEX.md                 8 行（唯一入口）
├── domain-<领域>.md × 8     一域一文件 ← 能力的最小单位
│     ├── frontmatter: name / intro / axis_* / keywords / domain / parts[]
│     └── 正文: ## 什么时候用 + ## 做法 1..N
├── _aliases.json            旧能力名 → 域能力名（历史账本兼容）
└── _archive/                17 个旧能力 + capabilities/_archive/CELLS.md（只读，⛔ 不再增长）
```

| 概念 | 现状 | 是不是"投递单位" |
|---|---|---|
| **能力** | **8 个域能力**（前端/后端/数据/文档/产品/环境·运维/求职·职业/AI-OS 自身） | 是（注入/提示都指向整个文件） |
| **做法（片）** | 41 条，写在各域文件 `parts:` 与正文「## 做法」 | **不是**（只是文件内的做法目录 + 校验单位） |

## 第一步：先判「该不该建」（Q5 闸门）

在动任何文件之前先答这三条，答不出就**不建**：

1. **移除后谁退化？**（Q5：没有它，哪类真实任务会明显变差）
2. **它属于哪个域？**（8 域之一；判不出 ⇒ 说明还没想清，先别建）
3. **它是"新动作"还是"已有动作的变体"？**（变体 ⇒ 走融合，不新增）

## 第二步：归域（判据 + 反例）

**判据：看它讲的是"哪个域的动作"，⛔ 不是"它可能在哪些域被用"。**

### 🔴 先查词表：这个词是「领域」还是「关注面」？（2026-11-02 v3 · 真实测试补的）

新能力常带一个**属性词**（性能 / 安全 / 成本 / 可维护性）。**先查 `task_cards/NEEDS-VOCAB.md`**：

| 它在词表里是哪一轴 | 处置 |
|---|---|
| **领域**（前端/后端/数据/文档/产品/环境·运维/求职·职业/AI-OS 自身） | 正常归域 |
| **关注面**（如「性能」= 快·延迟·吞吐·内存） | ⛔ **不许新开域**！同一词落两根轴会让坐标系自相矛盾 ⇒ 按"**它作用在哪个域的产物上**"分配（例：性能片作用在页面资源与渲染顺序上 ⇒ 归**前端**） |
| 两轴都没有 | 再考虑"是否真的需要它"（回 Q5） |

> 实例（2026-11-02 实测）：外来「性能优化」能力，5 条做法 ⇒ 归**前端** 3 片（`perf-budget` / `critical-path` / `measure-basis`），
> 没有新建 `domain-performance.md`。理由：性能是**关注面**，且开域会让后端/数据的性能动作变成两份真相。

| 判断 | 正确 | 错误 |
|---|---|---|
| 讲的是改代码/测试/调试/删码 | → **后端** | ⛔ 不要因为"公司叫它工程能力"就新建域 |
| 讲的是写/搬/拆/发文档 | → **文档** | ⛔ 不要因为文档是给"产品"写的就归产品 |
| 讲的是跨机部署/推送/git | → **环境·运维** | ⛔ 不要因为"部署也是代码"归后端 |
| 讲的是改数据本身（备份/回填/迁移） | → **数据** | — |
| 讲的是我们自己的工作流程（卡/账本/校验器） | → **AI-OS 自身** | ⛔ 不要归"通用"（没有这个域了） |
| 讲的是页面资源/渲染/交互 | → **前端** | ⛔ 不要因为"性能/安全"这类词就新开域 |

**允许把一个片拆到两个域**（例：`data-change-safety#migrate`→环境·运维，`#backup`→数据），
但**一个域文件不能因为"跨域"就复制同一片**（复制会产生两份真相）。

## 第三步：抽象（融合的实质）

**判据：两片若在做"同一件事的不同变体" ⇒ 合并成上位动作，变体降为做法举例。**

### 三问定生死（2026-11-02 v2 · 按两个真实融合测试的反馈落成操作化判据）

> ⚠️ 旧版 Q1「结果同类吗」太抽象：实测中同一批 6 条做法**既能**论证成"1 片"、**也能**论证成"6 片"，
> 判据本身挡不住糊弄。⇒ 落地成下面两个**可核对**的问题。

1. **产出物是不是同一种东西？**（读一段说明 / 写一段明文 / 改一个结构 / 出一条证据）
   例：`resume` 与 `pillars` 的产出物都是「按目标投影出的材料」⇒ 同类。
2. **缺了它的失败模式是不是同一类？**
   例：`tx-scope` 三条（事务边界/锁等待/旧值窗口）失败时都是「并发下假设不成立」⇒ 同类。
3. **它们的动作能用一个更上位的动词概括吗？**（投影 / 演练 / 划界 / 留退路 / 取证 / 收口）
4. **合并后，原变体还能作为一句"举例"保留吗？**（能 ⇒ 合并；不能 ⇒ 动作真的不同）
5. **动作类型是不是同一个？**（见下：**声明 vs 构造**是最常见的误并点）

### 动作类型维度（2026-11-02 新增 · 防"6 条压成 1 条空话"也防"6 条拆成 6 片"）

| 类型 | 你在干什么 | 典型动词 |
|---|---|---|
| **声明** | 把隐含契约写成明文 | 划界 / 写明 / 对齐 / 定判据 |
| **构造** | 造一个能扛住重复/撤销的结构 | 幂等 / 双写 / 回滚 / 重放 |
| **取证** | 造一条会失败的检查 | 复现 / 压测 / 交错证明 / 对账 |
| **读写** | 读权威层 / 写最小改动 | 对账 / 最小改 |

**硬规则**：同一片必须**共享同一动作类型**。两条若需要"并/且"连接两个不同动词才讲得通
（例：「声明并发边界」**且**「构造可重放变更」）⇒ **必须拆成两片**。
反测：若两条的产出物类型与失败模式都相同 ⇒ **不许拆**（拆了就是搬运）。

### 正例（求职域 7 片 → 5 片）

```
resume「按 JD 从经历库挑条目」
  + pillars「按四支柱看 README/代码/提交史/运行证据」
⇒ project-onto-target「把同一批事实按目标投影成不同产物」
   共同动作 = 投影；变体 = 投影成简历条目 / 投影成评审证据

interview「四段式演练」+ pitch「讲技术选择与困难解法」
⇒ rehearse「把材料在压力下讲出来」
```

### 正例（后端域 · 6 条做法 → 2 新片 + 并入 1 片，2026-11-02 真实测试）

```
①事务边界 ③乐观锁 ④旧值窗口   → 新片 tx-scope「划并发边界」
   产出物同为「并发成立前提的明文」· 失败模式同为「并发下假设不成立」· 类型=声明
②幂等 ⑤双写/兼容读/回滚开关   → 新片 replay-safe「留重放退路」
   产出物同为「重复施加或撤销后仍收敛」· 类型=构造
⑥并发取证（压测/交错证明/未复现标未验证） → 并入既有 narrow-check「最窄证据」
   产出物同为「一条会失败的检查」· 类型=取证
⚠️ ①③④ 与 ②⑤ **不合并**：需要「声明」且「构造」两个动词 ⇒ 动作类型不同
⚠️ ⑥ **必须并入**：三问全过还单列 = 搬运
```

### 反例（该保留的两个）

- `gaps-top3`（每个项目只给 3 条最高影响改进）**不并入** `project-onto-target`
  ⇒ 它是「**取舍输出**」，不是「投影」—— 产出物类型不同。
- `frontend-ui` 的 4 片（tokens / compose / rubric / ship）**全部保留**
  ⇒ 令牌→构图→评分→验收是四个**不同动作**，只是顺序相关。

## 第四步：落文件（字段规范）

只改目标域文件的 `parts:` 与正文「## 做法」，两处**必须一一对应**。

```yaml
# frontmatter parts（块式 list-of-map，⛔ 不写成行内 []）
- id: domain-docs#<动作短名>          # 必须 <文件名>#<短名>
  domain: 文档                        # 8 域之一（⛔ 不写"通用"）
  label: <短名>                       # ≤6 字
  one_line: <一句做法>                # ≤45 字，含"做"类动词
  from: [<旧片 id>, …]                # 出处 A：抽象自哪几片（可追溯到 _archive/）
  origin: <外部标准 / 本库真事 / 域 pattern 路径>   # 出处 B：**没有祖先**时用这个
```

```markdown
## 做法

7. **<短名>** —— <一句做法>
   > 出处：`<旧片 id>` · `<旧片 id>`
```

**域文件的其它字段**：`name`（`domain-x`）/ `intro`（一句"什么时候用"）/ `axis_domain` / `axis_help` / `axis_concern` / `keywords` / `merge_of`（合并自哪些旧能力）。

### 出处至少有一条（`from` 或 `origin`）

| 情形 | 用哪个 | 例 |
|---|---|---|
| 由旧能力/旧片抽象而来 | `from: [<旧片 id>…]` | `from: [doc_standards#structure]` |
| **全新动作、没有祖先**（外部 skill / 本库真事 / 领域 pattern） | **`origin: <来源>`** | `origin: 外部标准（Web Vitals 阈值）` / `origin: 本库真事 TASK-20260823-003 的 21x 失真` |

⛔ **不许编造旧 id 来填 `from`**（违反证据纪律）；⛔ 也不许留空 —— 至少一条且**可检索**。
> ⚠️ 2026-11-02 实测：`_capability_field_lint` **目前不校验 `from`/`origin`**（只校验 id/label/one_line/domain），
> ⇒ 本条是**人读判据**，别以为 lint 绿了就代表出处齐了。补机械校验是 follow-up。

### ⚠️ `intro` 与单测字面量耦合（改之前先查）

`tools/tests/test_task_card.py::test_claim_hint_cell_with_domain` 等用例把**域文件 `intro` 原文**写成了字面量断言
⇒ 改 `intro` 会红。两种处置：
1. **改 intro 并同步测试**（需 `tools/` 写域）
2. **不改 intro**，用 `axis_concern` + `keywords` 做新入口（多数维护卡的写域禁止动 `tools/` ⇒ 通常走这条）

## 第五步：校验（必跑，全绿才算完）

```bash
python tools/probes/_capability_field_lint.py        # 期望：8 OK / 0 WARN / 0 FAIL
python tools/probes/_capability_parts_matrix.py      # 期望：8 个域能力 / N 片 / 覆盖 8/8
python -m unittest discover -s tools/tests -p "test_task_card.py"
```

lint 会查：`id` 唯一且形如 `<文件名>#<短名>` · `domain` ∈ 8 域 · `one_line` ≤45 字且含动作词 · `label` 非空 · 片数 1–10。
⚠️ lint **不查** `from`/`origin` 是否存在（2026-11-02 实测）⇒ 出处齐全靠人核。

### 全局片数怎么同步（别指望单卡做完）

片数一变，「8 个域能力（50 片）」这类**全局读数**会在六件公开文档 / `capabilities/README.md` / `INVENTORY.md` 里过期。
但维护卡的写域通常**只含域文件 + INDEX** ⇒ ⛔ 不要为此越界改六件：

1. 本卡只同步 **`INDEX.md` 的片数 + 该域「什么时候用」列**
2. 交付里**列出**「全局读数已过期（旧值 N → 新值 M）」，由 lead 开**一张口径同步卡**统一改
3. 日常查询全局片数**一律以 `_capability_parts_matrix.py` 当次读数为准**（⛔ 不要引用文档里的数字）

## 反模式（都是真实踩过的）

| 反模式 | 为什么错 |
|---|---|
| **把两片拼成一片但不抽象** | 只是把文字接起来，动作还是两个 ⇒ 该保留两片 |
| **按"材料名"归域** | 「作品集/文档/数据」是**名词**，不是域；会判出 57% 准确率（实测） |
| **按阶段再拆一层** | class 区分力实测为 0（14/17 能力三阶段全占）⇒ 已废 |
| **新建第 9 个能力** | 一域一文件是硬口径；新东西要么进已有域，要么说明域不够 → 走 Human 裁决 |
| **复制同一片到两个域** | 两份真相，迟早漂移；跨域用一个片就够 |
| **新增「通用」桶** | Human 明确取消：通用做法按"能被用到的域"分配 |
| **忘了 `from:`** | 失去可追溯 ⇒ 以后没人知道这片的来源与依据 |
| **改了域文件 intro 却不改 INDEX 那列** | 2026-11-02 实测踩到：两处描述漂移，读 INDEX 的人以为后端只做代码 |
| **把「结果同类」当唯一判据** | 6 条做法既能被论证成 1 片、也能被论证成 6 片 ⇒ 必须叠「产出物类型 + 失败模式 + 动作类型」三问 |
| **为「属性词」新建域** | 性能/安全/成本在 `NEEDS-VOCAB` 里是**关注面**，不是领域；开域会让同一词落两根轴（2026-11-02 实测差点发生） |
| **越界去改六件公开文档的片数** | 维护卡写域通常不含它们；越界会撞车。正确做法 = 列 follow-up 给 lead 开同步卡 |

## 改动前后必须同步的伴生文件

> 🔴 2026-11-02 v2（按真实测试反馈）：原表把「必同步」与「告知 lead」混在一起，
> 与子任务的**写域约束**直接冲突（worker 只被允许改域文件 + INDEX 片数，
> 却被要求同步六件公开文档 ⇒ 要么违约、要么完不成）。⇒ 拆成两栏。

### A. 必同步（改完必须自己改，否则不一致）

| 文件 | 同步什么 |

| 文件 | 为什么不自改 |

## 附录 A：**真的新开一个领域**时要做什么（Human 裁决后才可走）

> 用户 2026-11-02 补充：「新增领域**不只是**新建域文件 + 检索之类，**还要把通用做法融进去**」。
> 因为「通用」桶已取消 —— 新域若只有它自己的专属动作、而不吸收与该域相关的通用做法，
> 它会是个**空壳域**：agent 照着做，却在"怎么自检 / 怎么改文件 / 怎么验证"这些通用面上一片空白。

必做清单（缺一条就不算建成）：

1. **Human 裁决**：为什么现有 8 域装不下（先走第二步的「领域 vs 关注面」判据）
2. **建文件**：`capabilities/domain-<x>.md`（frontmatter：`name`/`intro`/`axis_*`/`keywords`/`domain`/`merge_of`/`parts`）
3. **吸收通用做法（本轮新增的重点）**：从 8 个现有域里**找该域真会用到的通用片**，
   抽象后写进新域（例：任何域都要「先立可复现基线」「改文件守编码」「收口自证」⇒ 这些做法要有域内形态）。
   ⛔ 不是复制片（两份真相），而是**按新域的产物重新表述**；`origin:` 写明"通用做法在<域>的形态"。
4. **检索键**：`keywords` 覆盖该域真实词汇 + `axis_domain`/`axis_help`/`axis_concern` 齐备
   （否则检索 `matched=0`，能力等于不可见 —— 2026-11-02 实测过：域能力 `keywords` 只有 3 个时 `matched=1`）
5. **入口同步**：`INDEX.md` 加一行（含片数 + 「什么时候用」）、`_aliases.json`（若有旧名并入）、
   `CELLS`/矩阵脚本的 8 域常量、`capabilities/README.md` 的字段表
6. **全局读数**：六件公开文档 / INVENTORY 的「8 个域能力（N 片）」⇒ 交 lead 开口径同步卡

## 附录 B：**报错/踩坑不进能力，进经验**

> 用户 2026-11-02：「对于报错的东西，可以纳入**经验**，而不是能力」。

| 发现类型 | 去处 | 例（本轮真实发生） |
|---|---|---|
| **某个命令/脚本在特定环境下报错** | **经验**：`task_cards/memory/PITFALLS.md` + 对应经验族卡 | v4 卡给 `--stage` 把卡写坏（P92）· 脚本末行非 ASCII 在 GBK 控制台 exit 1（P93） |
| **某类任务反复退化的做法** | **能力**（域文件的片） | 「性能优化没有验收线 ⇒ 感觉快了」⇒ 前端 `perf-budget` |
| **某条判据算错了/口径漂移** | 经验（坑）+ 机械检查（lint/探针） | 「改了 intro 不同步 INDEX」⇒ 反模式 + lint 待补 |

判据一句话：**「下次别再这样」⇒ 经验；「这类活该怎么干得更好」⇒ 能力。**
⚠️ 坑还是要**落到机械检查**（lint / 探针 / 单测）才算闭环 —— 只写进 PITFALLS 而不加检查，下次照样踩。
